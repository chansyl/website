# 行人易安科技官网选题与设计方案

本方案将行人易安科技定位为面向企业的定制开发合作伙伴，围绕 **官网开发、定制网站开发、APP 开发、小程序开发** 四项已确认业务，展示技术能力和从需求到交付的工作方式。

已选主题为 **星际航线**，首页主张更新为“让你的企业，拥有自己的线上主场”。视觉采用深空黑、紫色轨道与宇宙地平线，表达从构想到产品的推进过程。设计以手机访问为优先，手机页面独立编排，详见 [手机网页设计方案](mobile-design.md)。完整页面文字以 [官网文案](website-copy.md) 为依据，重点说明企业官网的价值与电脑、手机两端的使用体验。

方案日期：2026 年 10 月 4 日。状态：第 3 张桌面视觉方向与独立手机方案均已获用户确认，现已按要求补充官网价值与双端体验文案；其他业务条款与资料未因此视为确认。当前只完成页面规划、文案和静态概念图，尚未开发代码。概念图中的符号 Logo、装饰英文和产品画面均为提案素材，不代表已确认品牌或真实客户成果；图中旧文案以后续文案稿为准。

## 一 品牌表达与访客目标

主要访客暂定为需要官网升级、定制业务网站、APP 或小程序的企业负责人、产品负责人和市场负责人。官网应帮助访客依次判断：你们做什么、能否理解我的需求、如何证明能力、合作后会拿到什么、怎样开始沟通。

对外定位建议：**围绕业务需求，提供网站与移动应用定制开发。**

品牌名称可以形成一条设计叙事：“行”对应推进与落地，“易”对应清晰沟通和降低使用难度，“安”对应可验证、可维护的交付。这是本次创意解读，不作为公司名称的官方释义，也不延伸为未经确认的安全资质或服务保证。

技术能力通过可操作的演示、产品结构与交付说明体现。暂不陈列未经确认的技术栈、客户 Logo、服务年限、项目数量、成功率、资质、响应时限或行业排名。

## 四 四项业务的区分

官网也是定制网站的一种。页面需要按客户目标区分“品牌展示”与“业务功能”，避免两个栏目只是同义重复。

| 服务 | 客户目标 | 可讨论的定制范围 | 建议呈现的交付物 |
| --- | --- | --- | --- |
| 官网开发 | 介绍企业、展示产品与服务、建立品牌信任 | 内容结构、视觉、响应式页面、多语言、搜索展示信息 | 页面设计、网站代码、静态资源、部署与维护说明 |
| 定制网站开发 | 把特定业务流程搬到线上 | 页面工作流、角色界面、表单、查询、数据展示、外部系统对接 | 功能清单、原型、约定范围内的代码、联调与验收材料 |
| APP 开发 | 提供独立移动端产品体验 | 核心使用流程、界面、终端能力、接口对接和发布准备 | 原型、应用工程、测试构建及约定的发布材料 |
| 小程序开发 | 在指定平台内触达用户和提供服务 | 展示、预约、查询、业务流程和平台能力对接 | 页面流程、工程代码、测试版本、平台提交材料 |

上表是方案组织方式，实际功能以项目范围为准。APP 的目标系统、原生或跨端方案，小程序的目标平台，以及后端是否由公司承接，均尚未确认；官网不提前承诺“全平台支持”或“包审核通过”。

本站本身遵循既有纯前端架构。对外介绍 APP、小程序与业务系统开发，不意味着本站要承载这些产品的后端功能。

## 五 页面信息架构

建议首期采用“完整首页 + 四个服务详情页 + 合作沟通页”。核心内容即使用户只浏览首页也能理解，详情页用于承接不同业务的进一步咨询。

| 页面 | 规划路径，均为公司站点内相对路径 | 主要内容 |
| --- | --- | --- |
| 首页 | `/` | 品牌主张、四项服务、定制说明、能力演示、交付流程、公司简介、联系入口 |
| 官网开发 | `/services/corporate-website/` | 品牌展示场景、内容组织、响应式体验、交付清单 |
| 定制网站开发 | `/services/custom-web/` | 业务流程、功能边界、交互与数据接口、验收方法 |
| APP 开发 | `/services/app/` | 用户场景、终端范围、开发方式讨论、测试与发布配合 |
| 小程序开发 | `/services/mini-program/` | 目标平台、使用流程、平台能力、交付与审核配合 |
| 合作沟通 | `/contact/` | 需求整理助手、真实联系方式、项目沟通说明 |

服务详情页使用统一结构：适合什么需求 → 能定制哪些部分 → 示例流程 → 交付清单 → 常见问题 → 沟通入口。根据内容差异调整布局，不复制四份相同正文。

首期导航建议为“服务能力、双端体验、交付流程、关于我们”，右侧固定主要按钮“聊聊建站需求”。首页导航跳转相应段落；服务条目进入详情页。移动端保留品牌、菜单和容易找到的联系入口。

真实案例不足时，不建立空的案例列表或案例详情路由；新闻、博客、招聘和会员系统暂不进入首期。

## 六 首页逐段设计

| 顺序 | 版块与任务 | 画面结构 | 交互与内容 |
| --- | --- | --- | --- |
| 1 | 首屏，让用户理解官网价值与公司业务 | 桌面居中标题、紫色轨道和地平线；手机靠左分行标题、偏右光弧，业务入口独立分组 | 轨道低幅流动；主要按钮去合作沟通页，次要按钮去双端体验 |
| 2 | 服务能力，让用户找到自己的需求 | 四条宽幅内容行，桌面可左右交替配图；避免密集卡片墙 | 每条写适用目标、典型范围和交付物，可进入对应详情页 |
| 3 | 官网价值，让客户理解建站的作用 | 四个简短价值说明：正式入口、完整介绍、统一分享、持续积累 | 自然阅读，不用虚构数据或紧迫感代替说明 |
| 4 | 双端体验，让技术可被体验 | 同一组内容的手机与电脑布局演示，配对应体验说明 | 当前设备对应状态优先，支持明确切换；标注“布局演示”，不冒充客户项目 |
| 5 | 定制与交付，让合作过程可预期 | 桌面横向四阶段，移动端纵向展开；先说明按业务确定范围 | 展示输入、产出与客户确认点，并将两端设计和验证纳入流程，不强制滚动播放 |
| 6 | 关于我们，建立具体而克制的品牌认知 | 清晰文字与安静背景，减少特效 | 先介绍业务和合作原则，团队、所在地、经营主体待补齐 |
| 7 | 联系与页脚，促成下一步沟通 | 大标题、主按钮、真实渠道和精简导航 | 官网不编造联系方式或模拟收件成功；主体与备案信息按实际情况补充 |

页面节奏为“品牌主张 → 业务入口 → 官网价值 → 双端体验 → 定制交付 → 联系”。双端演示承担主要技术展示任务，全页不同时运行多个抢眼场景。

### 技术能力的证明方式

优先用可检查的结果支撑能力说明：页面在不同屏幕下的展示、清晰可用的导航、键盘可操作的交互、可回溯的交付文档。后续有真实案例时，每个案例写“业务问题、负责范围、关键实现、实际成果”，成果数字只有在具备依据时发布。

不把本站使用的前端框架直接等同于公司已经掌握的全部 APP 或服务端技术。技术栈列表在你确认后再整理。

## 七 按需定制与交付体验

建议通过四阶段说明定制合作，而非用一张固定套餐价目表概括所有业务。

| 阶段 | 沟通输入 | 建议交付物 | 确认点 |
| --- | --- | --- | --- |
| 需求梳理 | 业务目标、用户、已有系统、预算范围、时间约束 | 需求清单、范围边界、优先级与里程碑建议 | 做什么、暂不做什么 |
| 原型设计 | 内容资料、品牌偏好、核心使用流程 | 页面结构、交互原型、视觉方案 | 流程与设计是否符合预期 |
| 开发验证 | 已确认方案、接口和环境条件 | 可体验版本、问题记录、验收清单 | 功能和体验是否达到约定标准 |
| 上线交付 | 账号、域名或平台条件、验收结果 | 约定代码与资源、部署说明、使用和维护材料 | 交付范围、责任与后续支持 |

这是建议的官网表述与服务流程，最终以你的实际合作方式为准。源码归属、版权、维护期限、报价、工期等由具体项目约定，不在设计稿中默认承诺。

合作沟通页可提供一个纯前端“需求整理助手”：选择业务类型，填写项目目标、已有资料和期望时间，生成可复制的沟通提纲。按钮应为“复制需求摘要”，并明确“未提交，仅在当前页面整理”。

主联系入口使用你提供的邮箱、电话或微信。若以后增加真正的在线提交，再单独确定收件服务和数据处理方式；首期不增加无接收端的提交按钮。

### 动效编排

| 部位 | 动效设计 | 桌面与移动端处理 |
| --- | --- | --- |
| 首屏 | 紫色轨道低幅流动，地平线轻微明暗变化；文字短距离淡入一次 | 桌面最多一个主要连续渲染场景；手机优先静态构图加低成本光效 |
| 服务条目 | 聚焦或悬停时细线和箭头响应 | 触屏直接可见必要信息，不依赖 hover |
| 需求切换 | 同一舞台内容交叉淡入，保留稳定高度 | 点击与键盘均可操作；切换不改变整页滚动位置 |
| 能力演示 | 由用户主动切换 Web、APP、小程序示意 | 设备模型和演示在需要时加载，不自动播放所有内容 |
| 交付流程 | 当前阶段沿一条细光路强调 | 手机改为纵向步骤，内容可直接阅读 |
| 联系区 | 一次轻微光线汇聚和按钮反馈 | 减少动态模式下使用静态状态 |

常规反馈约 160–240ms，内容进入约 400–650ms，背景循环约 12–20 秒，均为待调校的设计目标。尊重减少动态效果偏好；连续动效可暂停，离屏或标签隐藏时停止；不劫持滚动、不强制全屏开场、不添加跟随鼠标的装饰光标或频繁闪烁。

手机作为优先设计端，以 390px 宽、844px 高的参考视口规划首段信息，以可滚动长图展示下滑衔接。手机采用独立的标题分行、主视觉取景、业务入口、纵向流程和滚动后咨询入口；具体规则以 [手机网页设计方案](mobile-design.md) 为准。

## 十 与现有工程的衔接

沿用已完成的 React + Next.js 静态导出架构。公司标识暂建议 `xingren-yian`，仅为目录和 URL 标识，不是官方英文名；待确认后再创建。

- 源码规划：`sites/xingren-yian/`。
- 独立产物规划：`dist/xingren-yian/`。
- 汇总发布规划：`.pages/xingren-yian/`。
- 静态正文和 SEO 内容优先生成 HTML，Canvas 或 WebGL 仅承担装饰与演示，不能承载唯一的公司介绍或导航。
- 视觉动效先保留在公司目录。选定方向后，再确定是否需要 Motion 或一个图形运行库，不同时引入多套重叠动画依赖。
- 首屏静态底图与正文先呈现，重效果延后加载；页面在图形能力不可用时仍能阅读、导航和联系。

性能目标为首屏稳定、正文优先、无明显布局跳动。可在实现阶段以移动端 LCP 约 2.5 秒、CLS 不高于 0.1、INP 约 200ms 为优化目标，采用约定设备和网络实测；这些是目标，不是当前成绩或对所有访问环境的保证。

既有架构文档中的 Pages 托管适用范围仍然有效，最终上线目标需结合正式用途确定。本轮不创建发布配置。
